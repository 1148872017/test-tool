# 测试工作台 → 一站式测试平台 · 方案与执行计划

> ⚠️ **本文档已作废（2026-11-02）**。这里是最初的 70 人天全量规划，其中的 P2–P5（场景 Agent、AI 归因、自研 runner 等）已明确否决。
> **现行方案与进度请看：[平台规划与进度-2026-11-02.md](./平台规划与进度-2026-11-02.md)**，本文件仅作历史决策参考保留。

> 版本：v1（2026-10-30）
> 定位：**单人、本地、零部署**的测试工作台。不追公共平台功能全集，只把「每天真会打开」的那条链路做到顺手。
> 结论先行：技术上全部可行，但没有一个模块是「顺手就加」；真正的成本不在功能，在**数据模型、执行进程、以及三类引擎的长期维护**。建议按 P0→P5 分六段推进，**8 周可交出可用的 MVP，18 周可交出三件套**。

### 1.2 技术底座（决定后面能走多快）

- Electron 45 + React 18 + AntD 5 + esbuild 单文件 bundle；无原生模块，`npm install` 不需要 MSVC。
- sql.js（WASM SQLite）：**整库常驻内存 + 400ms 防抖整库重写**。配配置类数据够用，配执行结果会立刻变成瓶颈。
- 渲染层零网络请求；主进程只有 `shell:openExternal` 与文件对话框。
- 打包：`--dir` + 7za 出 zip（150MB），单文件 portable exe 需要在你自己机器上跑 `npm run dist`。
- 测试：主进程 25 项、迁移 15 项，`npm run test:main` / `test:migrate`。

**结论：底座够用，但有两处必须提前改：执行进程、结果存储。**

## 2. 产品定位与不做清单

### 2.1 定位

面向「公司不让装服务端 / 数据不出本机 / 只有一两个人在做测试」的场景：**打开即用的日常工具 + 能沉淀可回归资产**。

差异化不在功能数量，而在三件事：

1. 数据全在本机（明文永不外传）；
2. 资产是文本（md 用例、cURL 接口定义），可 Git、可 diff、可迁移；
3. 一条链路走到底（写用例 → 跑接口回归 → 看结果），而不是四个工具之间复制粘贴。

### 2.2 明确不做（写下来是为了以后不反复讨论）

| 不做 | 原因 |
| --- | --- |
| 服务端 / 多用户 / 权限体系 | 与「本地单机」冲突，工作量翻倍，且当前只有你一个人用 |
| 禅道集成 | 已决定剔除；只保留「粘贴 cURL / 导入 md」这类单向入口 |
| 周报模块 | 已剔除；趋势与统计在本地看板里做，不生成汇报文档 |
| 应用内生成 `.xmind` | XMind 官方支持 Markdown 导入，再实现一遍只会和它的行为打架 |
| 自研 HTTP 压测引擎 | k6 是天花板，自研只会在并发模型和指标上反复踩坑 |
| 自研浏览器自动化引擎 | Playwright 是天花板 |
| 重量级用例 DSL | 你已有成文标准（tess-s3-usecase + XMind_格式规范），应用只适配不定义 |
| 手工接口调试器（对标 Postman 全功能） | 打不过，也不需要；接口模块的目标是「能沉淀成可回归用例」 |

## 3. 模块设计逻辑

### 3.1 分层

```
数据层（已有）           执行层（新建）              聚合层（后置）
密码库 / 账号 / 笔记 / SQL → 用例 · 接口 · 回归 · 压测 · UI → 趋势 · 覆盖矩阵 · 报告
        ↑ 环境 / 凭据 / 变量 ←──────────────┘
```

设计原则：

- **数据层不依赖执行层**：即使执行层没做，密码库和笔记照样能用（现状即如此）。
- **执行层产出结构化结果**，聚合层只是查询；反过来（先做聚合）没有数据源，只能去爬别人。
- **文件为真源、数据库为索引**：md 用例与接口定义可 Git；DB 存索引与执行记录。

### 3.2 模块一：用例工作区（md 解析 + 校验 + 树视图）

**设计逻辑**：不新增编辑器，直接消费你现有的 `test_cases/**.md`。

- 输入：目录（建议指向 `D:\AI_Workspace\test_cases`，天然有 Git 与历史）。
- 解析：两种版式都要吃——
  - 标准 TC：`# 模块` / `## 分支` / `### 子分支` / `#### [风险][类型] 场景` + `- 前置/- 操作/- 预期`；
  - 极简链路：`## 链路名` + `> 覆盖回归流程` + `- **前置**/- **操作**(有序列表)/- **预期**` + `- [ ]`。
- 归一化字段：模块、分支、标题、风险（高/中/低，兼容 `[高风险]` 与 `[🔴高]` 两代写法）、类型、前置、操作（区分单行与 ①②③ 长链路）、预期子树（结果1..N / 三维断言迹 / 附加检查项）、`[覆盖 R…]`。
- 校验：把 `苔丝_backup\scripts\check_tc_format.py` 的规则（V8/V9/V11/V12/V13/V14）用 JS 重写，行号级定位；Python 脚本作为金标准做对拍测试。
- 展示：树视图 + 按风险/类型/关键词/覆盖规则筛选；点击定位到行。
- **只读**：应用永不回写 md（回写会破坏标准与 Git 历史）。

**可行性**：高。难点全在「格式容错」，不在技术。
**成本**：解析 4 天 + 校验 3 天 + 视图 3 天 + 覆盖矩阵 2 天 ≈ **12 天**（乐观 10 / 悲观 16）。

### 3.3 模块二：接口执行层

**设计逻辑**：把现有「接口记录（只复制）」升级为「可执行 + 可断言 + 可被用例引用」。

- 请求模型：method / url / headers / query / body / auth / 超时 / 证书策略；
- 环境与变量：环境 = baseUrl + 变量集（复用「网站管理」的站点概念）；变量作用域 全局 < 环境 < 用例，`{{var}}` 沿用现有实现；
- 断言：状态码、响应时间、JSONPath、文本包含、schema（后续）；
- 提取：从响应提取变量供后续步骤使用（链式）；
- 执行：主进程只做调度，真正发请求在 **runner 子进程**（见 3.7）；支持串行与有限并发；
- 导入：cURL（已能生成，反向解析即可）、HAR、OpenAPI（后续）、Postman collection（可选）；
- 证据：每次执行保存请求/响应快照（脱敏后落盘），失败可复现。

**可行性**：高。Node 侧无跨域、无浏览器限制，是三类里最确定的一块。
**成本**：请求模型 3 + 变量 3 + 断言 3 + 提取 2 + 执行器 2 + UI 3 + 历史 2 ≈ **18 天**（乐观 15 / 悲观 22）。

### 3.4 模块三：回归执行与报告

**设计逻辑**：用例（md）× 接口定义（DB）× 环境 → 一次 run。

- 用例里的「三维断言迹」决定可执行性：含 `API:` 的进入自动回归池；只有 `UI:`/`DB:` 的标记为「人工执行」；
- 套件 = 一个 md 文件 / 一个分支；支持标签筛选（`#冒烟`、`#p0`）；
- 失败重跑、跳过、中止；执行中可看流式进度；
- 报告：本地 HTML + JUnit XML（给 CI 留口）；每次 run 落 `runs/<runId>/`；
- 不做：定时调度（可用系统计划任务调 CLI，二期再考虑）。

**可行性**：高，主要是工程量。
**成本**：套件执行 3 + 报告 3 + 失败重跑 2 + 趋势 2 ≈ **10 天**（乐观 8 / 悲观 13）。

### 3.5 模块四：压测

**设计逻辑**：同一份接口定义，换一种执行器。

- 选型：bundle `k6.exe`（脚本化、有阈值、指标全）；轻量场景可选 autocannon（先用 k6 即可，不引第二套）；
- 场景配置：接口/链路 + 并发（VU）、时长、阶梯、阈值（p95 < 800ms、错误率 < 1%）；
- 生成 k6 脚本（JS）→ 子进程执行 → 解析 NDJSON 指标 → 实时曲线 → 报告；
- 数据参数化：CSV/JSON 数据池（与回归共用）；
- 防呆：生产环境二次确认 + 默认限速 + 只读接口白名单提示。

**可行性**：中高。k6 集成不难，难在「把压测配置做成界面可表达而不是写 JS」。
**成本**：集成 4 + 场景 UI 4 + 实时指标 3 + 阈值/报告 3 ≈ **14 天**（乐观 11 / 悲观 18）。
**风险**：单机上限约 1–2k RPS（受本机网卡与单进程限制）；要更高只能分布式，那就需要服务端，与定位冲突。

### 3.6 模块五：UI 自动化

**设计逻辑**：最后一个做，且有两种形态，建议先做轻的。

- 形态 A（轻）：应用托管一个 Playwright 工作区，界面负责「选择套件 / 选环境 / 点运行 / 看报告与 trace」，脚本由你（或 agent）写 TS。成本低、上限高、需要写代码。
- 形态 B（重）：应用内录制 → 步骤树 → 断言 → 套件。体验好，但选择器稳定性、等待策略、iframe/shadow DOM、登录态复用全是坑，录出来的步骤通常要人工修 30%–50%。
- 建议：**先 A 后 B**，A 验证「界面驱动执行 + 报告」这条链路，再决定要不要做录制。

**可行性**：中。技术可行，工程量大，且最容易烂尾。
**成本**：A 约 **8 天**；B 再加 **20–28 天**。

### 3.7 模块六：平台底座（先做，否则后面全要返工）

1. **runner 子进程**：Electron 主进程只做 UI 与调度；执行全部放 `utilityProcess.fork` / 子独立 Node 进程，通过 IPC 流式回报。理由：压测与浏览器自动化会长时间吃 CPU，塞主进程会卡死界面甚至被系统杀掉。
2. **结果存储与 sql.js 解耦**：config 留库；run / run_items / 产物落文件（JSONL + `runs/<id>/`）。否则一次批量回归触发几十次整库重写。
3. **数据模型 v3**：新增 `envs / vars / apidefs / cases(索引) / runs / run_items / artifacts`；旧 `records` 表与五个集合**原样保留**，不动老数据。
4. **CLI**：`testtool-cli run --suite ...`，供计划任务与 CI 使用（同一套 runner 代码）。
5. **脱敏**：日志与快照自动遮蔽 `password/token/cookie`，UI 上可查看但默认掩码。

**成本**：runner 3 + 存储改造 3 + 迁移 v3 2 ≈ **8 天**。

## 4. 可行性与风险

| 模块 | 技术可行性 | 主要失败模式 | 缓解 |
| --- | --- | --- | --- |
| 用例解析 | 高 | 格式版本漂移（skill 升级后新版式） | 版本探测 + 未知行保留 + 校验报告，不写回 |
| 接口执行 | 高 | 断言表达力不足，最后靠写脚本 | 断言先做 5 种覆盖 80% 场景，其余留脚本扩展 |
| 回归报告 | 高 | 结果太多把库写爆 | 结果落文件，库只存摘要 |
| 压测 | 中高 | 单机跑到瓶颈被误解为「工具不行」 | 报告里明确标注本机上限与客户端侧瓶颈 |
| UI 自动化 | 中 | 选择器漂移、等待不稳，维护成本高于收益 | 先做形态 A；提供 trace 与失败截图 |
| 整体 | — | 单人维护三类引擎，长期质量下降 | 分阶段验收，每阶段可独立停用；不达标就不进下一阶段 |

**体积影响**（当前 340MB 解包 / 150MB zip）：

| 增量 | 体积 | 何时加 |
| --- | --- | --- |
| Playwright Chromium | +130–150MB | P5 才需要；也可改为调用本机 Chrome（`channel: 'chrome'`）省掉 |
| k6 单文件 | +60–80MB | P4 |
| echarts（曲线） | +1MB | P2/P3 |
| 结果与产物 | 用户目录增长，按保留策略清理（默认留 20 次运行） | 全程 |

预计最终 **550–620MB 解包 / 230–260MB zip**。若在意体积：Playwright 用本机 Chrome，k6 做成可选下载。

## 6. 执行计划

### 6.1 阶段划分与验收（DoD）

| 阶段 | 周期 | 关键任务 | 验收标准（达不到就不进下一阶段） |
| --- | --- | --- | --- |
| P0 | 第 1–2 周 | 决策冻结（见 §7）、runner 骨架、v3 迁移、结果落盘、CLI `--version` | 迁移后旧数据零丢失、`test:migrate` 通过；runner 能跑一个假任务并回报进度 |
| P1 | 第 3–5 周 | 标准 TC 解析、极简链路解析、校验器、树视图、覆盖矩阵 | `test_cases/` 全部文件解析成功率 ≥95%；与 `check_tc_format.py` 判定差异为 0 |
| P2 | 第 6–8 周 | 请求模型、环境/变量、断言、提取、执行历史 | 真实跑通 ≥10 个自家接口；一条链式用例（登录→取 token→查询）通过 |
| P3 | 第 9–10 周 | 用例↔接口绑定、套件执行、报告、失败重跑 | 一次真实回归完整跑完并产出 HTML+JUnit；失败可重跑；结果可追溯 |
| P4 | 第 11–13 周 | k6 集成、场景 UI、实时曲线、阈值 | 对一个只读接口完成 100 VU × 2 分钟压测并出报告，指标与 k6 原生结果一致 |
| P5 | 第 14–15 周 | Playwright 工作区托管 + 运行 + trace 展示 | 选一个套件跑通，失败能看 trace/截图 |

### 6.2 里程碑

- **M1（第 8 周末）**：日常不需要再开 Postman 调自家接口。
- **M2（第 10 周末）**：用例文件零改动被解析，一次回归能在工具里跑完。
- **M3（第 13 周末）**：压测报告 5 分钟内产出。
- **M4（第 15 周末）**：UI 套件可在工具内触发并查看证据。

### 6.3 每周节奏

- 周一：确定本周 1–2 个可验收的交付点（写进 README 的「本周完成」）；
- 周三：中期检查，跑 `test:main` / `test:migrate` / 解析器 fixture；
- 周五：产出可交付物（zip 或可运行版本）+ 一句话结论「本周解决了什么，卡在哪」；
- 每阶段结束做一次「继续 / 裁剪 / 停」的复盘。

### 6.4 每阶段必须产出的东西（不只是代码）

1. 可运行产物（zip 或 `npm start` 可跑）；
2. 测试用例（主进程逻辑至少覆盖关键分支，fixture 驱动）；
3. README 更新（新增命令、目录、限制）；
4. 决策记录（ADR 追加，不覆盖旧记录）。

## 7. 关键决策（ADR 摘要）

| 编号 | 决策 | 理由 | 影响 |
| --- | --- | --- | --- |
| D1 | md 用例为**唯一真源**，DB 只做索引 | 你已有标准与 Git 资产；避免双写漂移 | 解析器必须容错；永不回写 |
| D2 | 执行放 **runner 子进程**，主进程只调度 | 压测/自动化会长时间吃 CPU | 多一层 IPC，但可换稳定性 |
| D3 | 结果与产物**落文件**，库只存摘要 | sql.js 整库重写，批量回归会写爆 | 需要保留策略与清理 |
| D4 | 压测用 **k6**，不自研 | 并发模型与指标是别人几年积累 | 体积 +60–80MB，需处理二进制分发 |
| D5 | UI 自动化**先做托管 Playwright 工作区** | 录制器成本高、维护高 | 需接受「要写 TS」 |
| D6 | 校验规则用 **JS 重写**，Python 脚本仅作对拍 | 不给你机器引入 Python 运行时依赖 | 需维护一份 fixture |
| D7 | 不引入服务端 | 单人本地，服务端只有成本 | 放弃多人协作与分布式压测 |
| D8 | 存储维持 sql.js（配置），必要时评估 `node:sqlite` | 避免原生模块破坏免编译构建 | 保留一次可能的存储迁移窗口 |

## 8. 数据模型草案（v3，新增表，旧表不动）

```sql
-- 环境：baseUrl + 变量 + 凭据引用
envs(id TEXT PK, name TEXT, base_url TEXT, vars TEXT, secret_refs TEXT, created_at INT, updated_at INT)

-- 变量（作用域 global / env / case），secret=1 时 value 走 safeStorage 加密
vars(id TEXT PK, scope TEXT, env_id TEXT, case_id TEXT, key TEXT, value TEXT, secret INT)

-- 接口定义（可执行）
apidefs(id TEXT PK, name TEXT, method TEXT, url TEXT, headers TEXT, query TEXT,
        body TEXT, auth TEXT, timeout_ms INT, env_id TEXT, assertions TEXT, extract TEXT,
        tags TEXT, created_at INT, updated_at INT)

-- 用例索引（来自 md，非真源）：file+mtime+hash 决定是否重解析
cases(id TEXT PK, file TEXT, module TEXT, branch TEXT, title TEXT, risk TEXT, type TEXT,
      steps TEXT, assertions TEXT, rules TEXT, line INT, hash TEXT, mtime INT)

-- 运行批次
runs(id TEXT PK, kind TEXT, env_id TEXT, suite TEXT, status TEXT,
     started_at INT, finished_at INT, stats TEXT, artifacts_dir TEXT)

-- 单条结果
run_items(id TEXT PK, run_id TEXT, case_id TEXT, status TEXT, duration_ms INT,
          message TEXT, assertions TEXT)

-- 产物（截图 / trace / k6 指标 / 请求响应快照）
artifacts(id TEXT PK, run_id TEXT, kind TEXT, path TEXT, meta TEXT)
```

**目录约定**

```
%APPDATA%\测试工作台\
  data.db / backups\ / runtime\ / debug.log        ← 现有
  runs\<runId>\{run.json, items.jsonl, artifacts\}  ← 新增
  cache\cases\<hash>.json                           ← 解析缓存（可删）
```

用例目录由用户指定（建议 `D:\AI_Workspace\test_cases`），不放进应用数据目录。
